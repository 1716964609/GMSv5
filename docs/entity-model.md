# GMS v5 — エンティティモデル

**文書バージョン：** Baseline 1.0  
**作成日：** 2026年10月20日  
**文書状態：** Product Owner決定反映済み・仕様ベースライン  
**対象範囲：** 論理ドメインモデル

---

## 1. モデリング原則

GMS v5は、ユーザーが自身の用語集を所有する用語管理・翻訳システムである。

一つの用語集（Glossary）は必ず一人のユーザーに所属し、一つの用語（Term）は必ず一つの用語集に所属する。

API認証情報（ApiCredential）もユーザー単位で保持する。

データモデルは現在の状態のみを表し、過去の変更履歴を管理しない。

翻訳リクエスト、機械翻訳の中間結果、最終訳文は一時的な処理オブジェクトとして扱い、業務データベースに永続化しない。

すべてのデータアクセスについて、サーバーは認証されたユーザーの所有権を検証する。

本論理モデルは、データベース製品、フレームワーク、インフラ構成を指定しない。

## 2. Entity：User（ユーザー）

GMSの登録済みアカウントを表す。

| 属性 | 意味 | 制約 |
|---|---|---|
| userId | ユーザー識別子 | 主キー |
| email | ログイン用メールアドレス | 必須・一意・変更不可 |
| displayName | 画面に表示する名前 | 変更可能 |
| passwordHash | アプリケーションが認証を管理する場合のパスワード検証値 | 機密情報・条件付き |
| authSubject | 外部認証サービスを使用する場合の本人識別子 | 条件付き |
| emailVerifiedAt | メール認証完了日時 | NULL可 |
| accountStatus | アカウント状態 | 必須 |
| createdAt | 作成日時 | 必須 |
| updatedAt | 更新日時 | 必須 |
| deletionRequestedAt | 削除要求日時 | NULL可 |
| deletionScheduledAt | 最終削除予定日時 | NULL可 |

### 2.1 アカウント状態

- `PENDING_VERIFICATION`：メール認証待ち
- `ACTIVE`：通常利用可能
- `PENDING_DELETION`：削除確定後、恒久削除までの内部保持期間中

### 2.2 不変条件

- メールアドレスはアカウント単位で一意とする。
- ユーザー自身によるメールアドレス変更を許可しない。
- 表示名とメールアドレスを別属性として管理する。
- メール認証済みかつ`ACTIVE`のユーザーのみ通常ログインできる。
- `PENDING_DELETION`のユーザーは通常機能へアクセスできない。
- 一般ユーザー向けのADMIN/USERロール階層を設けない。
- パスワードの平文は保存しない。

### 2.3 認証情報の管理主体

外部のマネージド認証サービスへ認証処理を委任する場合、パスワードハッシュは原則として認証サービス側で管理し、GMS側に重複保存しない。

アプリケーション自身がパスワード検証を担当する場合は、安全なソルト付きパスワードハッシュを保存する。

具体的な方式は認証設計時に一つ選択する。

## 3. Entity：Glossary（用語集）

ユーザーが所有する名称付き用語集合を表す。

| 属性 | 意味 | 制約 |
|---|---|---|
| glossaryId | 用語集識別子 | 主キー |
| ownerUserId | 所有ユーザー識別子 | 必須・外部キー |
| name | 用語集名 | 必須 |
| description | 用語集の説明 | 任意 |
| createdAt | 作成日時 | 必須 |
| updatedAt | 更新日時 | 必須 |

### 3.1 リレーション

`User 1 : 0..N Glossary`

`Glossary 1 : 0..N Term`

一人のユーザーは複数の用語集を所有できる。

一つの用語集には複数の用語を格納できる。

### 3.2 不変条件

- 一つの用語集は必ず一人のユーザーに所属する。
- 閲覧・更新・削除・インポートは所有者のみ実行できる。
- 保存された現在状態を唯一の正とする。
- アプリケーションレベルのバージョン番号や履歴を保持しない。
- 用語集削除時には、所属用語も削除する。
- 空の用語集も存在できる。

## 4. Entity：Term（用語）

原語と訳語を対応付ける一つの多言語用語ペアを表す。

| 属性 | 意味 | 制約 |
|---|---|---|
| termId | 用語識別子 | 主キー |
| glossaryId | 所属用語集識別子 | 必須・外部キー |
| sourceLanguage | 原語の言語コード | 必須 |
| targetLanguage | 訳語の言語コード | 必須 |
| sourceTerm | 原語表現 | 必須 |
| targetTerm | 対応する訳語表現 | 必須 |
| description | 用語に関する説明 | 任意 |
| createdAt | 作成日時 | 必須 |
| updatedAt | 更新日時 | 必須 |

### 4.1 リレーション

`Glossary 1 : 0..N Term`

### 4.2 不変条件

- 一つの用語は一つの用語集に所属する。
- 一つの用語レコードは、一つの原語と一つの訳語を対応付ける。
- `sourceLanguage`と`targetLanguage`は翻訳方向を表す。
- 同一用語集内で、`sourceLanguage`、`targetLanguage`、`sourceTerm`、`targetTerm`の4属性が、原語・訳語の前後空白除去およびUnicode NFC正規化後にすべて一致する場合だけ重複とする。
- 英字の大文字・小文字は区別する。同一原語に異なる訳語を持つTermは同時に存在できる。
- 異なる用語集間では、同じ4属性を持つTermも許容する。
- 更新時は現在レコードを書き換え、過去バージョンを新規作成しない。
- 用語へのアクセス可否は所属用語集の所有権で判定する。
- 所有者以外は用語を参照・編集・翻訳選択できない。

### 4.3 多言語対応例

英語から日本語：

`EN → JA：heart failure → 心不全`

日本語から英語：

`JA → EN：心不全 → heart failure`

これらは別々の翻訳方向を持つ用語レコードとして扱う。

一方向の登録から逆方向の対応を自動生成することは前提としない。

### 4.4 用語集間の重複

異なる用語集では、同じ原語に異なる訳語を登録できる。複数の用語集から競合候補を同一翻訳リクエストに選択した場合、永続データを変更せず、リクエスト単位でユーザーに候補を提示して一つを選択させる。解決前に外部APIを呼び出さず、AIが代理選択してはならない。

## 5. Entity：ApiCredential（API認証情報）

ユーザーが登録した外部翻訳サービスのAPIキーを表す。

| 属性 | 意味 | 制約 |
|---|---|---|
| credentialId | 認証情報識別子 | 主キー |
| userId | 所有ユーザー | 必須・外部キー |
| provider | `DEEPL`または`OPENAI` | 必須 |
| encryptedSecret | 暗号化されたAPIキー | 必須 |
| createdAt | 登録日時 | 必須 |
| updatedAt | 最終更新日時 | 必須 |

### 5.1 リレーション

`User 1 : 0..2 ApiCredential`

一人のユーザーが登録できるのは、DeepLとOpenAIのAPIキー各1件、合計最大2件とする。

### 5.2 一意性制約

`(userId, provider)`の組み合わせを一意とする。

同じプロバイダーの有効なAPI認証情報を複数保持しない。

### 5.3 ライフサイクル

**登録**

選択した外部サービスのAPIキーを保護した状態で保存する。

**置換**

新しいAPIキーを登録し、以前の保存値を破棄する。

**削除**

APIキーを削除し、以後の翻訳に利用できない状態にする。

**アカウント削除要求**

ユーザーの保存済みAPIキーを直ちに無効化・削除する。

### 5.4 セキュリティ制約

- 登録後、APIキーの平文をクライアントへ返却しない。
- APIキーをログ、トレース、エラーメッセージに含めない。
- 他ユーザーのAPIキーを翻訳処理へ使用しない。
- 秘密情報は暗号化とアクセス制御で保護する。
- 暗号化方式や鍵管理方式はセキュリティ設計段階で決める。

## 6. アカウント削除ライフサイクル

アカウント削除は、状態変更と一定期間経過後のデータ削除から構成する。

### 6.1 状態遷移

通常のライフサイクル：

`PENDING_VERIFICATION → ACTIVE → PENDING_DELETION → DELETED`

`DELETED`は、業務システム上でアカウントが削除済みであることを意味する。

### 6.2 内部保持期間

削除要求の正式確定時点から**30暦日**保持する。これはユーザー向けの復旧猶予期間ではない。

削除要求の最終確認直後に、通常のアプリケーション利用を停止する。

アカウント情報、用語集、用語は内部的に保持するが、ユーザーおよび通常業務機能から利用できない。

APIキーは削除要求時に削除し、復元しない。

30日保持期間が終了したら残存業務データを恒久削除する。

### 6.3 最終削除の依存関係

データの削除は、関連関係を考慮した順序で行う。

1. 子EntityであるTerm
2. 親EntityであるGlossary
3. その他のユーザー所有データ
4. Userレコードおよび該当する外部認証ID

データベースのカスケード削除やトランザクションを利用してもよい。

途中失敗時に安全に再実行できるよう、削除処理には冪等性を持たせる。

### 6.4 復旧条件

GMS v5はアカウント復旧を提供しない。`PENDING_DELETION → ACTIVE`および`DELETED → ACTIVE`の状態遷移は存在しない。

### 6.5 保存期間に関する扱い

30日内部保持は製品独自のデータ保持・削除ポリシーである。

別途適用される法的保存義務や技術的バックアップの保存期間は、通常の業務データの30日保持と区別して取り扱う。

## 7. 外部認証サービスとの連携

メール認証とパスワード回復は、対応する外部認証サービスに委任する。

GMSの論理的な要求は以下とする。

- メール認証手続きの開始
- メール認証完了状態の確認
- 無効・期限切れの認証情報の拒否
- パスワード回復手続きの開始
- パスワード再設定用認証情報の検証
- 認証セッションの開始・失効

### 7.1 EmailVerificationの扱い

外部認証サービスがトークン発行、有効期限、確認、再利用防止を完全に担当する場合、GMS側に独立したEmailVerificationテーブルを設ける必要はない。

アプリケーション側では、必要な外部ユーザー識別子とメール認証済み状態を参照・保持する。

メールの送信のみを外部委託する場合は、トークンのライフサイクルを別途実装する必要がある。

最終的な責任分界は認証設計時に決定する。

## 8. 一時オブジェクト：TranslationRequest

一回の翻訳要求を表す非永続オブジェクト。

| 属性 | 意味 |
|---|---|
| requesterUserId | 認証済みユーザー識別子 |
| originalText | ユーザーが入力した原文 |
| sourceLanguage | 翻訳元言語 |
| targetLanguage | 翻訳先言語 |
| selectedTermIds | 複数用語集から選択した用語ID集合 |
| consentConfirmed | 外部送信への同意確認状態 |

### 制約

- リクエスト実行者は認証済みかつ`ACTIVE`であること。
- 選択できる用語は最大10,000件とする。
- 用語選択ゼロ件も有効とする。
- すべての選択用語の所有権をバックエンドで検証する。
- TranslationRequest自体を業務データベースに保存しない。

## 9. 一時オブジェクト：TranslationContext

翻訳処理中だけ保持する実行時情報。

| 属性 | 意味 |
|---|---|
| effectiveTermPairs | 認可済みかつ翻訳方向に適合した用語集合 |
| translationProviderConfiguration | 外部翻訳プロバイダーの実行時設定 |
| initialTranslation | DeepLが返却する一次翻訳結果 |
| postEditedTranslation | OpenAIが返却する最終訳文 |

### 9.1 中間訳の必要性

DeepLによる一次翻訳結果は、GPTによるポストエディティングの入力となる。

そのため、**一時オブジェクトとしての中間訳は必要**である。

ただし、専用の永続EntityやDBテーブルは必要としない。

### 9.2 翻訳処理の流れ

1. 選択された用語IDを取得する。
2. 所有権と言語ペアを確認する。
3. 翻訳用の一時的な用語コンテキストを構築する。
4. DeepL APIを呼び出す。
5. 一次翻訳結果を処理中のメモリに保持する。
6. 原文、一次翻訳結果、関連用語情報を使ってOpenAI APIを呼び出す。
7. 最終訳文を返却する。
8. リクエスト終了後、一時的な処理データを解放する。

## 10. 一時オブジェクト：TranslationResult

| 属性 | 意味 |
|---|---|
| translatedText | 翻訳成功時の最終訳文 |
| executionStatus | `SUCCESS`または`FAILURE` |
| errorCategory | 失敗理由の区分。任意 |

成功した翻訳として返却するのは、後編集まで完了した最終訳文のみとする。

DeepLの中間訳を、最終的な翻訳成功結果として扱わない。

## 11. Entity間の関係

| 親Entity | 子Entity | 多重度 |
|---|---|---|
| User | Glossary | 1 : 0..N |
| Glossary | Term | 1 : 0..N |
| User | ApiCredential | 1 : 0..2 |
| User | 認証サービス上のIdentity | 論理的に1 : 1 |

TranslationRequestとTranslationResultは永続Entityではないため、DB上の永続リレーションを持たない。

## 12. データアクセス制御

すべての業務データ取得・変更処理では、認証済みユーザーを条件として適用する。

所有権検証の対象には以下を含める。

- 用語集の一覧取得
- 用語集の作成・更新・削除
- 用語の一覧取得
- 用語の作成・更新・削除
- 用語検索
- JSONインポート
- 翻訳時の用語選択
- APIキーの設定・更新・削除
- プロフィールの変更
- アカウント削除・恒久削除

クライアントから渡されたIDが存在することだけでは、アクセス権限を認めない。

## 13. ページネーションのデータ契約

### 13.1 用語集一覧

取得要求には以下を含める。

- ページ識別子またはページ番号
- 最大100件のページサイズ
- 安定した表示順序

レスポンスには、要求ページのデータと、次ページの有無などのページ情報を含める。

### 13.2 用語一覧

用語集IDを指定し、同様のページ単位で取得する。

バックエンドは用語集の所有権を検証する。

各ページ要求では新たにデータを取得する。
