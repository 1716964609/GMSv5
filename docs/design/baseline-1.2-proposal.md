## 2. CR-01 — Bulk Term Selection Performance（未承認・未実装）

### 2.1 現行コードの調査結果

2026年11月8日に作業ツリーのソースを読み取り確認した結果を示す。Product Owner報告値は10,000件で約40秒。これは本番環境を独立に計測・再現した値ではない。

| 項目 | コードから確認した現状 |
|---|---|
| ページ取得方法 | `src/lib/translation/term-page-loader.ts` の `fetchAllPages()` が1ページを `await` してから次ページを要求する逐次取得。ページ間の並列取得はない。 |
| ページサイズ | `src/lib/validation.ts` の最大ページサイズと `src/lib/db/repository.ts` の `listTerms()` は100 Term/ページ。 |
| 10,000件の要求数 | すべて未取得なら100ページ。展開時に1ページ目がキャッシュ済みなら通常は残り99ページを要求する。 |
| 1ページごとのDB処理 | `listTerms()` はGlossary所有権を確認した後、Term総数の `COUNT(*)` と、`created_at DESC, term_id ASC` 順の最大100件のSELECTを行う。 |
| 選択反映 | BYO画面は全ページ取得成功後にTerm ID集合を作り、既存選択との和集合・10,000件上限を判定してから選択状態を反映する。 |
| 失敗・中止・世代 | ページ取得はAbortSignalを受け、Glossary単位の要求世代を確認している。古い応答や中止を選択反映に使わない設計である。 |

SQLiteは単一DBファイルへの読み取り負荷、同一プロセス内の同期DB処理、I/O待ち、他のAPI処理との競合を考慮する必要がある。並列HTTP要求を増やしてもSQLite処理が同率で速くなるとは限らず、ロック待ち、CPU・メモリ使用量、他要求の遅延を悪化させる可能性がある。

### 2.2 提案する方式

全ページ並列取得ではなく、同時実行数に上限を置いた並列取得を候補とする。最初の評価候補はSelect Allの1操作あたり **2ページ** と **4ページ** の同時取得とする。ページ応答の順序に依存しない形でページ番号を保持し、全ページが揃った後にのみ元のページ順で検証・選択する。

別GlossaryのSelect All操作が重なった場合も、画面セッション内で要求数が無制限に積み上がらないようにする。初期候補の上限は、同一タブ内のTermページ取得合計で最大4件とし、4ページ並列の単一操作と複数操作の合計を区別して計測する。これは実装方式を決める仕様ではなく、Product Owner承認前の負荷制御提案である。

APIの現在の `page=N` 契約と100件単位のレスポンスを維持できる見込みである。ページ応答の結合を並列化するだけならAPI契約やDBスキーマ変更は前提としない。計測でページごとの重複COUNTやORDER BYが主要ボトルネックと判明した場合に限り、集約取得・専用一括API・適切な索引などを別の設計変更として比較検討する。現時点でDB変更を要件化しない。

ただし現行Term一覧は`LIMIT/OFFSET`であり、並列ページ要求中に別操作で同Glossaryへ用語が追加・削除されると、ページ境界がずれて重複・欠落する可能性がある。Select All開始時点の同一Term集合を保証するには、読み取りスナップショットを一つの処理内で扱う一括取得API、または同等の安定カーソル/スナップショット契約が必要になる可能性がある。初期の比較試験はデータを固定して逐次/並列の負荷差を測り、機能受入には同Glossaryの同時変更を含むケースを追加する。スナップショット保証の方式を決める場合も、DBスキーマ変更は別途根拠が示されない限り前提にしない。

### 2.3 データ完全性・中止条件

- 翻訳要求全体で選べる上限は10,000 Term IDとする。既存選択と対象GlossaryのID集合の和集合で判定し、同一IDは一度だけ数える。
- Select Allは取得対象ページの全件が成功し、ページ番号・総ページ数・Term ID集合の完全性を確認できた後に限り確定する。
- 1ページでも失敗した場合、ページ取得中にユーザーが折りたたみ・画面離脱した場合、または取得結果が不完全な場合は、その操作での部分選択を一切追加しない。既存選択は保持する。
- 同時実行中の残り要求は不要になった時点で中止する。中止を通常のAPIエラーとして見せない。
- 古い世代の応答は、現行のTerm一覧・選択状態・選択件数を更新しない。
- ページ移動、折りたたみ、再展開後も明示解除されていない選択を維持する。
- 10,000件超過時はSelect All全体を拒否し、部分集合を成功表示しない。個別選択と既存の用語なし翻訳ルールは維持する。

### 2.4 性能測定案と提案受入条件

比較は隔離された合成10,000 Termデータで行い、DeepL/OpenAI呼び出しを含めない。逐次取得（同時数1）と同時数2・4を、同一アプリケーション版、同一DBファイル、同一ページサイズ、同一インスタンスタイプの本番相当小型EC2（現行As-Built記録上はt4g.small）で比較する。DBのウォーム/コールド条件を固定して記録し、各条件でウォームアップ後に最低10回測る。

**暫定性能目標（Product Owner承認が必要）：**

- 10,000件 Select All 完了時間のp95を20秒以下にする。
- 逐次取得基準のp95に対して50%以上短縮する。基準p95が40秒で再現した場合、20秒以下が同等の目標となる。
- 同時Termページ取得数が提案上限を超えない。
- 同じデータで選択されたTerm IDが期待する10,000 IDと完全一致し、重複・欠落がない。失敗・中止試験では既存選択が不変で、新規IDが0件追加である。
- 同一負荷時にCPU、RSSメモリ、DB busy/lock等のエラー、ページAPI p50/p95、他の軽量APIのp95を記録する。暫定ガードとして他API p95を逐次基準の2倍以内とする案を提示する。測定データとEC2余力を見て最終値をProduct Ownerが決める。

比較レポートには、環境・データ生成方法・各試行時間・中央値/p95・リクエスト数・最大同時実行数・CPU/RSS・DBエラー・全件一致結果を記録する。1/2/4の中で、完全性と安定性を満たしたもののうち負荷を過度に増やさない設定を採用する。p95目標が達成できない場合は並列度だけを無制限に上げず、DB/API側の改善を別提案にする。

## 3. CR-02 — Public Landing Page Modernization

### 3.0 Product Owner変更記録（2026年11月8日）

### 3.1 情報設計

1. **Header：** 左に「GMS」の暫定ワードマーク。中央または右側に「機能」「使い方」「プライバシー」「よくある質問」のページ内リンク、ログイン、新規登録。モバイルではメニューを折りたたんでもよいが、ログイン・登録と全アンカーにキーボードでアクセス可能にする。

6. **FAQ (`id="faq"`)：** 用語集・APIキー・データ送信・GMS内の保存・料金など、実仕様に基づく質問と回答を提示する。GMSサービス自体は無料、DeepL・OpenAI API料金は各サービスの契約条件に従い発生する場合があると区別する。

### 3.2 確定した日本語コピー

ブランド改名は行わず、Headerでは暫定的に「GMS」を維持する。本文ではサービス用途を先に説明し、GMS v5のバージョン番号をHeroの大きな訴求文に使わない。

**ヒーロー見出し**  
専門用語の翻訳を、もっと思いどおりに。

**補足**  
ご自身の用語集を管理し、翻訳に使う用語を選べます。DeepLで一次翻訳し、OpenAIで訳文を整えることで、専門分野の翻訳作業をサポートします。同じ原語に複数の訳語がある場合は、翻訳前に候補を確認して選択できます。

**CTA**  
主：新規登録  
副：ログイン  
新規登録CTAには「無料」を単独で付けず、サービス料金と翻訳API料金の違いが利用者に伝わる表現にする。GMS自体は無料で利用でき、DeepL・OpenAI API料金は各サービスの契約条件に従い発生する場合がある。

**機能紹介**

- 用語をまとめる：用語集を作成し、用語を登録・検索。対応JSONからのインポートもできます。
- 必要な用語を選ぶ：翻訳に使う用語だけを選択。選択内容はその翻訳リクエストに適用されます。
- 訳語候補を確認する：同じ原語に複数の訳語がある場合、翻訳前に候補を選べます。

**プライバシー説明**  
翻訳には、ご自身のDeepLおよびOpenAI APIキーを設定してください。キーは保護された状態で保存し、画面に平文では表示しません。翻訳を実行すると、同意した原文と選択用語がDeepLへ送信されます。用語を選択した場合は、DeepLで翻訳に使う一時用語集を作成し、翻訳後に削除を要求します。OpenAIへは原文、DeepLの中間訳、選択用語が送信されます。原文、中間訳、最終訳文はGMSの業務データベースへ永続保存しません。外部サービス側での処理やデータ保持はGMSが保証するものではありません。[DeepLのプライバシー情報](https://www.deepl.com/en/privacy)および[OpenAI APIのデータ管理説明](https://developers.openai.com/api/docs/guides/your-data)をご確認ください。API利用料金は各サービスとの契約に従います。

**FAQ候補**

- どのようなサービスですか：自分の用語集を管理し、翻訳に使う用語を選んで専門用語翻訳を支援するサービスです。
- 用語を登録できますか：用語集画面で登録・検索でき、対応JSONをインポートできます。
- 翻訳に必要なものは何ですか：ユーザー自身のDeepLとOpenAI APIキーを設定します。
- どのデータが外部送信されますか：同意後、原文と選択用語がDeepLへ送られ、OpenAIへ原文、中間訳、選択用語が送られます。選択用語がある場合、DeepL向けに一時用語集を作成し、翻訳後に削除要求を行います。
- 翻訳内容は保存されますか：GMSの業務データベースには原文・中間訳・最終訳文を永続保存しません。外部サービス側の処理・保持は各サービスの説明を確認してください。
- 利用料金はいくらですか：GMSは無料でご利用いただけます。翻訳に使用するDeepL・OpenAIのAPI利用料金は、各サービスの契約条件に従います。料金が発生する場合の金額や無料枠は各サービスの契約内容をご確認ください。

**表現ルール：**GMS自体が無料であることは明記できるが、「すべての翻訳が完全無料」「API料金もGMSが負担する」「無制限に無料で翻訳できる」と表現しない。API料金はDeepL・OpenAI各サービスの契約条件に従い発生する場合があると説明する。「完全に安全」「データを一切保存しない」「AIが正確に翻訳」など確認できない安全性・保存・品質の断定をしない。「GMSの業務DBに翻訳本文を永続保存しない」と「翻訳サービスへ送信する」を同時に明示する。DeepLの削除要求を外部サービス側での削除完了保証と表現しない。

### 3.3 確定したデザイン方向

### 3.3.2 タイポグラフィと余白

- 日本語本文は読み慣れたサンセリフ体とし、OS標準フォントを優先して外部フォントの追加通信を避ける。ブランド名や短い英字ラベルは補助的に使い、本文は自然な日本語にする。
- ヒーロー見出しは一つに絞り、本文の行長・行間・段落間隔を確保する。太字の連続や極端に細いウェイトを避け、モバイルでも見出しが過度に改行しないようにする。
- 余白は一定の間隔体系を使って階層化する。各セクションを広く取る一方、機能紹介とCTA間の移動を長くしすぎない。

### 3.5 アニメーション・動画

- 初回リリースは静的な装飾を基本とする。重い背景動画、音声・動画の自動再生は使わない。
- CSSアニメーションは控えめな短い状態変化に限り、情報やCTAの表示をアニメーションに依存させない。
- `prefers-reduced-motion`が指定された場合、装飾的な移動・拡大・スムーズスクロールを抑止し、アンカー移動は即時に完了する。
- 動画は初回リリースの必須要件にしない。将来追加する場合は別途Product Owner承認を受け、任意再生、軽量ポスター、字幕または全文、キーボード操作、低減モーション対応、性能測定を追加条件とする。

### 3.6 性能・アクセシビリティ・SEOの検証方針

**性能（提案受入条件）**

- 代表的なモバイル端末とデスクトップで、キャッシュ条件を分けて最低10回計測する。初期HTML、主要画像、フォント、JavaScript転送量、LCP、INP、CLSを記録する。
- 暫定目標は実ユーザーまたは同等のフィールドデータの75パーセンタイルで、LCP 2.5秒以下、INP 200ミリ秒以下、CLS 0.1以下とする。ローカル/Lighthouseのラボ値だけで合格としない。
- 動画は初期ロードに含めず、主要画像は適切な寸法・形式・圧縮を行う。コンセプト用の画像がLCP要素となる場合は優先度と容量を個別に測る。
- LCP/INP/CLSの目標値と75パーセンタイル評価は[web.dev Core Web Vitals](https://web.dev/articles/vitals)の指針に基づく。指標は将来更新され得るため、実装・公開時に再確認する。

**アクセシビリティ（提案受入条件）**

- WCAG 2.2 AAを設計・評価の目標とする。キーボードだけでSticky Header、アンカー、CTA、FAQを利用でき、フォーカスが見えること。アンカー先の見出しとフォーカス位置をSticky Headerが隠さない。見出し階層、リンク名、画像代替テキスト、色コントラスト、拡大表示時のリフローを確認する。
- FAQの開閉はキーボードと支援技術で識別・操作できること。自動検査に加えてキーボード、スクリーンリーダー、200%拡大、モーション低減を手動確認し、自動検査だけで適合を断定しない。
- 適合基準の参照：[W3C WCAG 2.2](https://www.w3.org/TR/WCAG/)。

**SEO（提案受入条件）**

- 日本語の固有な`title`、説明的なmeta description、1つの主見出し、意味のある見出し順、クロール可能な通常リンク、適切なcanonical、OGP画像/文言、faviconを確認する。
- 公開ページはサーバー描画された本文と認証リンクを含み、JavaScriptが無効でも主要説明を読めること。プライバシー情報を画像内だけに置かない。
- sitemap/robotsの公開URLとインデックス方針を確認し、ログイン・登録・個人ページを誤ってインデックスさせない。構造化データは内容が事実と一致すると確認できる場合にだけ追加する。
- 検索結果の表示や順位を保証しない。タイトル・説明・構造化データの検証は[Google Search Central](https://developers.google.com/search/docs/appearance)を参照する。
