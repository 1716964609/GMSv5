# GMS v5 — 要件定義書

**文書バージョン：** Baseline 1.0  
**作成日：** 2026年10月20日  
**開発方法論：** AI Unified Process（AIUP）  
**文書状態：** Product Owner決定反映済み・仕様ベースライン  
**対象範囲：** アプリケーションソフトウェア要件

## 1. 製品概要

GMS v5は、個人ユーザー向けの多言語対応・用語集連携型翻訳Webアプリケーションである。

各ユーザーは、アカウント登録、専用用語集の管理、JSONファイルからの用語インポート、選択した専門用語を使用した翻訳を行うことができる。

翻訳処理には、DeepLによる機械翻訳とOpenAI GPTによるポストエディティングの2段階方式を採用する。外部翻訳APIの認証情報は、ユーザー自身が登録する。

認証後のアプリケーションは、次の3画面で構成する。

1. 用語集管理（Glossary Management）
2. BYO翻訳（BYO Translation）
3. 設定（Settings）

未認証ユーザー向けには、製品紹介、アカウント登録、ログインの入口となる公開ランディングページを提供する。

各ユーザーの用語集、用語、アカウント設定、API認証情報は、他ユーザーから論理的に分離される。

翻訳原文、中間翻訳結果、最終翻訳結果は、アプリケーションの業務データベースに永続保存しない。

### 1.1 基本設計原則

- **Bring Your Own Glossary：** ユーザー自身が用語集を提供・管理する。
- **Bring Your Own API Key：** ユーザー自身がDeepLおよびOpenAIのAPIキーを登録する。
- **データ所有権の分離：** 各ユーザーは自身が所有する業務データのみを操作できる。
- **Single Source of Truth：** 保存されている用語データの現在状態を唯一の正とする。
- **データ最小化：** 翻訳本文は処理時にのみ使用し、永続化しない。
- **多言語対応：** 各用語は原語と訳語の言語情報を明示的に保持する。
- **仕様駆動開発：** 実装技術に依存せず、要件とユースケースから振る舞いを定義する。

## 2. アクター

| アクター | 役割 |
|---|---|
| 訪問者（Visitor） | 公開ページの閲覧、登録・ログインの開始 |
| メール未認証ユーザー（Pending User） | 登録後、メール認証の完了待ち |
| 有効ユーザー（Active User） | 用語集管理、翻訳、設定を利用 |
| 認証サービス（Authentication Provider） | 認証、メール確認、パスワード回復 |
| DeepL API | 第1段階の機械翻訳 |
| OpenAI API | 第2段階のポストエディティング |

有効な一般ユーザーはすべて、自身のデータに対して同等の機能権限を持つ。

## 3. 機能要件

### 3.1 公開ランディングページ

**FR-101 — 公開アクセス**

未認証の訪問者は、ランディングページを閲覧できること。

**FR-102 — ヘッダーの配置**

ランディングページの上部中央に、横長のヘッダーパネルを配置する。

デスクトップ画面では、左から順に以下の要素を配置する。

- ブランド画像
- アプリケーションタイトル
- ログインボタン
- 新規登録ボタン

ブランド画像にはクリック可能な外部プロフィールへのリンクを設定する。

ブランド画像とタイトルはヘッダーパネルの左側、ログイン・新規登録ボタンは右側に配置する。

**FR-103 — メインコンテンツ**

ヘッダーの下に、より大きな中央配置の情報パネルを設ける。

デスクトップでは左右おおむね均等な2領域に分割する。

左側には以下を表示する。

- 製品概要
- 主な機能
- 利用方法
- お知らせ・更新情報
- 必要に応じた免責事項

右側には以下を表示する。

- プライバシーに関する説明
- 外部APIへのデータ送信に関する説明
- 開発者情報
- 連絡先

説明文は、実際の製品仕様を正しく反映すること。実態と異なる静的アーカイブや外部送信なしの説明を表示してはならない。

**FR-104 — フッター**

メインパネルの下に中央配置のフッターを設置し、著作権表記、年号、必要なサービス通知を表示する。

**FR-105 — デザイン**

基本配色は、落ち着いたラベンダー色と白色の組み合わせとする。

| 要素 | 色 |
|---|---|
| 基本ラベンダー | `#9B9BC7` |
| 基本ホワイト | `#FFFFFF` |
| 明るい背景色 | `#F7F7FA` |
| 主な文字色 | `#30303C` |

薄いグラデーション、控えめな影、角丸、自然な画面遷移を使用する。

背景には、下部に向かって明るくなる柔らかいラベンダー系グラデーションを用いる。

**FR-106 — レスポンシブ対応**

画面幅に応じてヘッダーやメインコンテンツの寸法を変更し、重要な操作要素が隠れないこと。

狭い画面では、左右の説明領域を上下に配置してもよい。

### 3.2 ユーザー登録・認証

**FR-201** 訪問者はメールアドレスとパスワードを使用して登録できること。

**FR-202** 同一メールアドレスに対して複数の有効アカウントを作成できないこと。

**FR-203** 登録直後のアカウントは、メール認証が完了するまで未認証状態とすること。

**FR-204** メール未認証のアカウントでは保護されたアプリケーション画面へログインできないこと。

**FR-205** 認証サービスが提供する確認リンクなどを利用してメールアドレスを検証できること。

**FR-206** 認証情報の有効期限、再送回数、試行制限には選定した認証サービスのセキュリティポリシーを適用すること。

**FR-207** メール認証済みユーザーは、メールアドレスとパスワードでログインできること。

**FR-208** ログイン成功後は用語集管理画面へ遷移すること。

**FR-209** 認証済みユーザーはログアウトできること。

**FR-210** 現行の認証フローでは多要素認証（MFA）を使用しないこと。

**FR-211** 一般ユーザーに管理者・閲覧者などのロール選択機能を設けず、各ユーザーが自身のデータを管理できること。

**FR-212** 公開ログイン画面に「パスワードを忘れた場合」の入口を設置すること。

**FR-213** パスワード回復には、有効期限と再利用防止機能を備えた認証サービスの仕組みを使用すること。

**FR-214** 無効・期限切れ・使用済みの認証情報による本人確認を拒否すること。

### 3.3 認証後のナビゲーション

**FR-301 — ナビゲーションドロワー**

認証後の各ページには、左上に3本の横線で構成されるハンバーガーメニューを設置する。

操作すると、左側から縦長のナビゲーションドロワーが展開する。

**FR-302 — メニュー項目**

ドロワー上部には以下を配置する。

1. Glossary Management
2. BYO Translation

ドロワー下部には、上部項目と視覚的に区切ってSettingsを配置する。

**FR-303** メニュー項目を選択すると、対応する画面へ遷移すること。

**FR-304** 認証後の画面遷移ではログインセッションを維持すること。

**FR-305** ドロワーはメニュー操作または閉じる操作で折りたためること。

**FR-306 — デスクトップ表示の自動伸縮**

ドロワーが閉じた状態では、用語集管理画面を5つの均等な機能列で構成する。

`検索 | 用語集一覧 | 用語集詳細 | 用語一覧 | 用語詳細`

ドロワーが開いた状態では、左側に追加領域を配置する。

`ドロワー | 検索 | 用語集一覧 | 用語集詳細 | 用語一覧 | 用語詳細`

開いたドロワーと5つの機能列は、おおむね同一の比例幅で画面を分割する。

ドロワーを開いても、既存の機能列を非表示にしないこと。

**FR-307** 6列表示では可読性を確保できない画面幅の場合、すべての機能へアクセスできるレスポンシブ構成に切り替えること。具体的なモバイル配置は後続のUI設計で決定する。

### 3.4 用語集管理

**FR-401 — 5カラム構成**

用語集管理のメイン領域は、幅がおおむね均等な5つの縦長パネルから構成する。

**第1列：検索**

- 上部にキーワード入力欄を表示する。
- 入力欄に隣接して検索ボタンを設置する。
- 下部に検索結果一覧を表示する。
- 検索結果を選択すると、該当する用語集と用語の情報を詳細パネルに表示する。

**第2列：用語集一覧**

- ログインユーザーが所有する用語集名を一覧表示する。
- 用語集の選択により、第3列と第4列を更新する。
- パネル内にページ切り替え操作を配置する。

**第3列：用語集詳細**

- 上部に「新規作成」「更新」「削除」ボタンを配置する。
- 選択中の用語集名と説明を表示する。
- JSONインポートの入口を、上部の操作エリアまたはヘッダー付近に配置する。
- 作成・更新時はモーダルダイアログなどで編集可能にする。

**第4列：用語一覧**

- 選択された用語集に所属する用語を一覧表示する。
- 用語を選択すると第5列を更新する。
- パネル内にページ切り替え操作を配置する。

**第5列：用語詳細**

- 上部に「新規作成」「更新」「削除」ボタンを配置する。
- 原語の言語
- 訳語の言語
- 原語
- 訳語
- 説明
- 所属用語集

これらの属性を表示し、作成・更新操作時には編集可能にする。

**FR-402** ユーザーは自身が所有する用語集のみ閲覧できること。

**FR-403** 用語集名と任意の説明を指定して、新規用語集を作成できること。

**FR-404** 自身の用語集名と説明を更新できること。

**FR-405** 自身の用語集を削除できること。

**FR-406** 用語集を削除した場合、その用語集に所属する用語も削除すること。

**FR-407** 選択した用語集の用語一覧を取得できること。

**FR-408** 自身の用語に対して作成・参照・更新・削除の各操作を実行できること。

**FR-409** 各用語は原語言語、訳語言語、原語、訳語、任意の説明を保持すること。

**FR-410** 一つの用語レコードは、一つの原語表現と一つの訳語表現の対応を示すこと。

**FR-411** 同一Glossary内で、次の4属性を正規化後にすべて一致する場合だけ重複と判定し、登録・更新・インポートを拒否すること。

- `sourceLanguage`
- `targetLanguage`
- `sourceTerm`
- `targetTerm`

`sourceTerm`と`targetTerm`は前後の空白を除去し、Unicode NFC正規化して比較する。英字の大文字・小文字は区別する。同一原語に異なる訳語を持つTermは同一Glossary内に同時に存在できる。異なるGlossary間の重複は許容する。

**FR-412** 用語集および用語は現在状態のみを保持し、アプリケーションレベルの過去バージョンを保存しないこと。

**FR-413 — ページネーション**

第2列と第4列では、サーバー側ページネーションを使用する。

- 用語集一覧：1ページ最大100件
- 用語一覧：1ページ最大100件
- 前後のページまたはページ番号への移動操作を提供する
- ページ切り替えのたびにバックエンドへ新規データ取得要求を送信する
- 全データを取得してからブラウザ側だけで分割する方式は使用しない
- 選択中の用語集を変更した場合、用語一覧は1ページ目から表示する

**FR-414** 作成・更新・削除・インポート後には、関連する表示データを再取得して更新すること。

### 3.5 用語検索

**FR-501** ユーザーは自身の用語をキーワードで検索できること。

**FR-502** 検索対象に原語と訳語を含めること。

**FR-503** 検索結果から一致した用語と所属用語集を識別できること。

**FR-504** 検索結果を選択すると、用語集および用語の詳細を表示できること。

**FR-505** 他ユーザーの用語を検索結果に含めないこと。

### 3.6 JSON用語集インポート

**FR-601** JSONインポート機能は用語集管理画面に配置すること。

**FR-602** ユーザーはローカルのJSONファイルを選択できること。

**FR-603** インポート先として新しい用語集を作成できること。

**FR-604** 既存の自分の用語集をインポート先に指定し、用語を追加できること。

**FR-605** 各インポート項目には、原語言語、訳語言語、原語、訳語を含めること。

**FR-606** 1回のインポート上限は10,000用語ペアとすること。

**FR-607** 登録前にJSONの構造と各項目を検証すること。

**FR-608** 正常に登録された用語は、検索・CRUD・翻訳時の選択対象として利用できること。

**FR-609** インポート時にも手動登録と同じ用語の一意性制約を適用すること。

**FR-610** 不正なインポート、重複違反、既存データとの衝突はエラーとして扱い、バッチ内の1件でも失敗した場合は全件を登録しないこと（All-or-Nothing）。既存Glossaryの正常なTermを置換・削除してはならない。

**FR-611** JSONはトップレベルに`terms`配列だけを持ち、各項目は`sourceLanguage`、`targetLanguage`、`sourceTerm`、`targetTerm`を必須とし、`description`を任意の文字列として受け付ける。未定義の追加属性、必須属性の欠落、型不正を検証エラーとする。エラーには項目位置と理由を含める。新規Glossary作成と同時の失敗時はGlossaryも作成しない。

### 3.7 BYO翻訳

**FR-701 — 原文入力**

翻訳画面にOriginal Text入力欄を設けること。

**FR-702 — 言語設定**

翻訳元言語と翻訳先言語を選択できること。対応言語は外部翻訳サービスの仕様に従う。

**FR-703 — 用語集選択**

ユーザー自身が保存した用語集を一覧表示し、複数選択できること。

**FR-704 — 用語表示**

用語集を選択または展開すると、所属用語を表示すること。

**FR-705 — 一括選択**

展開された各用語集にSelect All操作を設け、対象用語を一括選択できること。

**FR-706 — 個別選択**

各用語をチェックボックスで選択・選択解除できること。

**FR-707 — 複数用語集からの選択**

異なる用語集から選択した用語を、一つの翻訳リクエストに集約できること。

**FR-708 — 選択状態の表示**

選択済み用語の件数を表示し、選択内容を確認できること。

**FR-709 — 用語なし翻訳**

用語を一つも選択しなくても翻訳を実行できること。

**FR-710 — 選択件数上限**

一つの翻訳要求で使用する用語は最大10,000ペアとすること。

**FR-711 — 外部送信の同意**

翻訳画面には、原文と選択した用語がユーザー自身のAPI認証情報を使用してDeepLおよびOpenAIに送信されることを説明する同意チェックボックスを設ける。

初期状態は未選択とし、チェックされるまでTranslateボタンを無効にする。

**FR-712 — 翻訳処理**

処理順序を次のとおりとする。

1. リクエスト、同意状態、API認証情報を検証する。
2. 選択された用語の所有権を検証する。
3. データベースから現在の用語情報を取得する。
4. 指定された翻訳言語に対応する一時的な翻訳用語集を構築する。
5. 同一原語・同一翻訳方向に異なる訳語候補がある場合、候補を表示し、ユーザーが一つを選択するまで外部APIを呼び出さない。
6. すべての原語について有効な訳語対応が一意に定まったことを確認する。
7. DeepLによる一次翻訳を実行する。
8. OpenAIによるポストエディティングを実行する。
9. 最終訳文を返却し画面に表示する。

**FR-713 — 固定モデル**

OpenAIの利用設定は次の値に固定する。

- モデル：`gpt-6-luna`
- 推論レベル：`medium`

ユーザー向けモデル選択画面は設けない。

**FR-714 — エラー処理**

DeepLが失敗した場合、OpenAIの後続処理を実行しないこと。

OpenAIが失敗した場合、中間訳を完成済みの最終訳文として表示しないこと。

**FR-715 — 翻訳データの非永続化**

原文、DeepL中間訳、最終訳文を業務データベースへ保存しないこと。

**FR-716 — 用語集の読取専用利用**

翻訳の実行によって保存済み用語集・用語を変更しないこと。

**FR-717 — 結果表示**

最終訳文を翻訳画面上に表示すること。

**FR-718 — TXTダウンロード**

最終訳文をTXT形式でダウンロードできること。

**FR-719 — 同時翻訳の制限**

同一翻訳ページでは、一度に一つの翻訳リクエストのみ実行する。翻訳処理中はTranslateボタンを無効化する。

**FR-720 — サーバー側認可**

選択された用語IDの所有権をバックエンドで検証し、クライアントが送信した用語本文を無条件に正として扱わないこと。

**FR-721 — 翻訳候補の衝突解決**

翻訳リクエスト単位で、同一翻訳方向・同一原語に異なる訳語が対応する場合は候補を表示し、ユーザーが一つを選択するまで翻訳を開始しない。永続Term、Glossary、保存済み用語データは変更しない。AIがユーザーに代わって選択してはならない。対象候補は複数Glossaryにまたがる。同じ原語・同じ訳語の候補は衝突としない。

**FR-722 — 外部API上限の扱い**

一つの翻訳リクエストで最大10,000 Termペアを選択できる。外部APIの入力サイズまたは用語集制限を満たせない場合は明示的なエラーを返し、用語の自動削減・自動省略・分割処理を行わない。

### 3.8 設定画面

**FR-801** 設定画面はナビゲーションドロワー下部から開けること。

**FR-802** 自身のメールアドレスと表示名を確認できること。

**FR-803** 表示名を変更できること。

**FR-804** メールアドレスは読取専用であること。

**FR-805** 有効な認証セッションを持つユーザーは、追加のアプリケーション独自の再認証操作を要求されずにパスワード変更を開始できること。

**FR-806** DeepL APIキーを登録・置換・削除できること。

**FR-807** OpenAI APIキーを登録・置換・削除できること。

**FR-808** ユーザーごとにDeepL用、OpenAI用の有効なAPIキーを各1件のみ保持すること。

**FR-809** APIキーを置換する際は以前の保存値を破棄し、履歴を保持しないこと。

**FR-810** 保存済みAPIキーの平文を画面へ再表示しないこと。

**FR-811** APIキーが不足する場合、翻訳処理を開始せず、設定画面への案内を表示すること。

**FR-812** 設定画面の最下部に、他の設定項目と区別されたアカウント削除領域を配置すること。

### 3.9 アカウント削除・保持・恒久削除

**FR-901 — 削除入口**

設定画面の最下部に、赤色などの破壊的操作を示すアカウント削除ボタンを配置する。

**FR-902 — 二段階の意思確認**

削除には以下を必要とする。

1. ユーザー自身による削除操作の開始
2. 現在のパスワード入力
3. 削除結果を説明する独立した最終確認

**FR-903 — 即時利用停止**

最終確認後、アカウントを削除待ち状態（PENDING_DELETION）に移行し、通常のログインとサービス利用を停止する。

**FR-904 — 内部保持期間**

削除要求の正式確定時点から30暦日、アカウント情報、Glossary、Termを内部的に保持する。これはユーザー向けの復旧猶予期間ではなく、アカウント復旧機能を提供してはならない。通常のログインとサービス利用は直ちに停止する。

**FR-905 — API認証情報**

削除要求時点でDeepL・OpenAIのAPIキーを使用不能にし、保存済みの認証情報を削除する。

**FR-906 — 保持中の利用停止**

30日間保持するアカウント情報、Glossary、Termは、ユーザーからも内部の通常業務機能からも利用できない状態とする。

**FR-907 — 最終削除**

30暦日経過後、アカウントに関連する残存業務データ、Glossary、Termを恒久削除する。削除済みアカウントは復旧できない。

**FR-908 — 保存期間の説明**

内部30日保持、法令上の保存義務、技術的バックアップの保持期間を相互に区別して説明する。法令・バックアップ上の保持は、ユーザー向け復旧機能を意味しない。

**FR-909 — 廃止番号**

UC-017に対応していたアカウント復旧機能の要件は廃止する。番号は再利用しない。

| ID | 分類 | 要件概要 |
|---|---|---|
| NFR-SEC | セキュリティ | 不正アクセス、入力攻撃、資格情報漏えい、不正利用からシステムを保護する。データアクセスは、入力値をSQL文の構造として解釈させないパラメータ化等の安全な方式で実行し、SQLインジェクションを防止する。具体的なORM・DB製品は確定しない |

| NFR-REL | 信頼性 | 外部APIの失敗や途中終了を一貫した方式で扱う |
| NFR-AVAIL | 可用性 | 合意された稼働条件下でサービスを利用可能にする |
| NFR-PERF | 性能 | 一覧・検索・翻訳処理を適切な要求単位で実行し、必要に応じてページネーションする |
| NFR-MAINT | 保守性 | 認証、用語集管理、翻訳の責務を明確に分け、変更・検証しやすくする |
| NFR-TEST | テスト容易性 | 登録、認可、CRUD、インポート、翻訳、削除を自動テストできる |
| NFR-USE | 使用性 | 一貫した画面構成、明確なエラー表示、削除確認、操作しやすいUIを提供する |

| NFR-OBS | 観測性 | APIキーや翻訳本文を不必要に記録せず、処理失敗の原因を調査可能にする |
| NFR-REC | データ保持・削除 | 削除確定後は通常利用を直ちに停止し、業務データを30暦日内部保持した後に恒久削除する。ユーザー向け復旧機能は提供しない |
| NFR-GOV | データガバナンス | 個人情報の収集、外部送信、保持、削除、用語データの権利について適切に説明する |

具体的な実装技術およびデプロイ構成は、論理的な製品要件とは別に設計する。
